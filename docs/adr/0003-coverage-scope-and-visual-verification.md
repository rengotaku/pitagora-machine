# ADR 0003: カバレッジ対象を純粋ロジックに限定する

## 背景

物理シミュレーションと Canvas 描画には、単体テストで検知できない壊れ方がある。実際にこのプロジェクトで起きたものを挙げる。

| 不具合 | 検知した手段 |
|---|---|
| 矩形パーツが全て画面から消える（Matter.js は全ボディに `circleRadius: 0` を持つため、`undefined` 判定で円/矩形を分けると全て半径 0 の円になる） | 実ブラウザのスクリーンショット |
| 回転ホイールの 2 枚の羽根が重なって 1 本になる | codex レビュー + スクリーンショット |
| 通過検知用のセンサー矩形が画面に見えている | スクリーンショット |
| シーソーが傾いたまま戻らずボールが溜まる | 実ブラウザでの計測（回収回数の異常） |
| 低 fps でセンサー通過を取りこぼして循環が止まる | 低 fps を模擬した実測 |

いずれもテストは緑のままだった。jsdom では `canvas.getContext("2d")` が `null` を返すため、描画コードを呼ぶテストは早期 return して**何も検証していない状態でも通る**。

一方でカバレッジのしきい値を全ファイルに課すと、検知できない対象を分母に含めることになり、しきい値を満たすために「意味のないテストを足す」「使っていないファイルを消す」という本末転倒が起きる。

## 決定

**1. カバレッジ対象は `src/lib/**` のみ**（しきい値 80%）。

分岐を持つ純粋ロジック（固定タイムステップ・停滞検知・投入判断・分岐選択・ドミノ復帰・ボール個体差・総数管理・押し出し・設定値のクランプ・パネルの状態遷移）をここに置く。

**2. 装置の組み立て（`src/machine`）と描画（`src/render`）はカバレッジ対象外。**

構築のスモークテストは置くが、これらの正しさは実測とスクリーンショットで担保する。

**3. 「非自明な実装」では実装前にテストケース仕様を固定する。**

状態を持つロジック・時間依存・モックが必要なものは、実装者に設計を委ねず、前提・手順・期待挙動・検証観点を先に決めてから実装する。実装とテストを同じ視点で同時に書くと、両方が同時に間違っても検知できない。

**4. 検証は数値とスクリーンショットの両方を毎回セットで残す。**

数値だけでは「詰まって同じ位置で止まっているボール」に気づけない。画像だけでは例外でループが止まっていても直前のフレームが正常に見える。

**5. エラー収集は未処理例外と `console.error` の両方を購読する。**

`Runtime.exceptionThrown` は未処理例外しか通知しない。`try/catch` で握って `console.error` に流された異常は `Runtime.consoleAPICalled` でしか拾えず、片方だけだと「エラー 0 件」という判定が嘘になる。

## 捨てた案

- **jsdom で Canvas をモックして長時間シミュレーションをテストする**: 一度実装されたが不採用にした。ダミーの 2D コンテキストで数千ステップ回しても、実ブラウザの描画・レンダリングタイミングとは別物で、上表の不具合はどれも検知できない
- **全ファイルにカバレッジしきい値を課す**: 検知できない対象を分母に含めることになる
- **`canvas` パッケージ（node-canvas）を入れて jsdom で実描画する**: 依存が増えるうえ、ブラウザの Canvas 実装とは挙動が異なる。実ブラウザで測るほうが確実

## 変えてよい前提 / 壊すと危ない前提

- **変えてよい**: しきい値の数値、`src/lib` に置くモジュールの粒度、検証の間隔と回数
- **壊すと危ない**:
  - **判定ロジックを `src/machine` や `src/render` に書いてカバレッジ対象から外すこと**。分岐は `src/lib` に置く
  - **スクリーンショットを確認せず数値だけで合格にすること**。上表の不具合はすべて数値が正常なまま起きた
  - **エラー収集を片方だけにすること**。合格条件そのものが検証できなくなる
